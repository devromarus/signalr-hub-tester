# SignalR Hub Tester

Мини-приложение для интерактивного тестирования SignalR-хабов с поддержкой авторизации через Bearer-токен. Чисто клиентское решение — не требует серверной части.

## Возможности

- Подключение/отключение к SignalR-хабу с авторизацией через токен
- Сохранение истории подключений (последние 10) в `localStorage`
- Вызов методов хаба (Invoke) с валидацией JSON-параметров
- Подписка на события хаба (On) с отображением в реальном времени
- Приём потоковых данных (Server-to-Client Streaming) с отменой
- Журналирование всех операций с фильтрацией, поиском и экспортом в JSON
- Маскирование токена и защита от XSS

## Запуск локально

### Требования

- **Node.js 22.22.0** (указано в `engines` в `package.json`). Рекомендуется использовать [nvm](https://github.com/nvm-sh/nvm) для управления версиями:

  ```bash
  nvm install 22.22.0
  nvm use 22.22.0
  ```

- **npm** (поставляется вместе с Node.js).

### Установка зависимостей

```bash
npm install
```

> **Примечание.** В проекте есть файл [`.npmrc`](.npmrc) с флагом `legacy-peer-deps=true`. Он необходим, т.к. пакеты `@alfalab/core-components` содержат конфликтующие peer-зависимости (`react-virtual` требует React 16/17, а проект использует React 18). Флаг применяется автоматически при установке.

### Запуск в режиме разработки

```bash
npm run dev
```

Клиент запускается на `http://localhost:5173` (порт задан в [`vite.config.ts`](vite.config.ts)). При изменении кода страница обновляется автоматически (HMR).

### Сборка для продакшена

```bash
npm run build
```

Собранные файлы размещаются в `dist` и могут быть развёрнуты на любом статическом хостинге.

### Предпросмотр продакшен-сборки

```bash
npm run preview
```

Локальный сервер для проверки собранного `dist` (по умолчанию на `http://localhost:4173`).

## Запуск через Docker

Приложение можно быстро развернуть в контейнере с помощью Docker Compose. Готовый билд (`dist`) уже включён в репозиторий, поэтому **не требуется ни Node.js, ни локальная сборка** — достаточно только Docker.

> **Почему билд хранится в git?** Установка зависимостей `@alfalab/core-components` внутри контейнера падает из-за известного бага npm 10.x «Exit handler never called!» (конфликтующие peer-зависимости `react-virtual`). Поэтому готовый `dist` собирается заранее и хранится в репозитории, а Docker только раздаёт его через nginx.

### Требования

- Docker 20.10+
- Docker Compose v2

### Запуск

```bash
docker compose up -d --build
```

Приложение будет доступно по адресу `http://localhost:8080`.

### Остановка

```bash
docker compose down
```

### Полезные команды

```bash
# Просмотр логов
docker compose logs -f web

# Полная остановка с удалением контейнера
docker compose down --remove-orphans
```

### Обновление билда (для разработчиков)

Если вы вносите изменения в исходный код, пересоберите `dist` и зафиксируйте его в git:

```bash
npm run build
git add dist
git commit -m "Обновлён билд"
```

### Структура Docker-файлов

| Файл | Назначение |
|---|---|
| [`Dockerfile`](Dockerfile) | Раздача готового `dist` через nginx (без этапа сборки) |
| [`nginx.conf`](nginx.conf) | Конфигурация nginx: SPA fallback, кэширование, gzip |
| [`docker-compose.yml`](docker-compose.yml) | Описание сервиса, проброс порта `8080:80` |
| [`.dockerignore`](.dockerignore) | Исключение лишних файлов из контекста сборки |

## Деплой на GitHub Pages

Готовый билд (`dist/`) уже включён в репозиторий и собран с относительными путями (`base: './'` в `vite.config.ts`), поэтому его можно раздавать прямо со страницы репозитория без пересборки в CI.

> **Почему не пересобирается в CI?** Пакет `@alfalab/core-components` публикуется во внутренний корпоративный npm-registry и недоступен с публичных раннеров GitHub Actions. Поэтому `dist` обновляется вручную (см. раздел «Обновление билда» выше) и коммитится в репозиторий.

Чтобы включить GitHub Pages:

1. Запушьте репозиторий на GitHub.
2. Перейдите в **Settings → Pages**.
3. В блоке **Build and deployment** выберите **Source: Deploy from a branch**.
4. Укажите branch `main` и папку `/dist`, нажмите **Save**.
5. Через 1–2 минуты приложение будет доступно по адресу `https://<username>.github.io/<repo-name>/`.

## Ограничения

- **CORS**: приложение подключается к хабу напрямую из браузера, поэтому целевой хаб должен разрешать CORS для origin приложения. Для хабов, блокирующих CORS, потребуется прокси-сервер.
- **Токен**: хранится только в памяти и не сохраняется между сессиями (SR-01). В `localStorage` сохраняется только URL хаба.

## Безопасность

- Токен авторизации не сохраняется в локальном хранилище (только в памяти)
- Токен маскируется в интерфейсе (первые и последние 4 символа)
- Входящие данные от хаба экранируются перед отображением (защита от XSS)
